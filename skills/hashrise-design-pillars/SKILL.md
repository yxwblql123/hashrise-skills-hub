# 设计支柱与漂移检查

多数小团队的设计文档会越写越长、越写越散，最后没人说得清"这个游戏到底是什么"。**设计支柱**是解决这件事的最小机制：3–5 条，每条配一个可判定的反例。

## 支柱的写法

每条支柱有四个要素，缺一不可：

| 要素 | 作用 | Hashrise 实例 |
|------|------|-------------|
| **名称** | 一个能记住的短语 | 真实挂机的经济张力 |
| **说明** | 一句话讲清含义 | 电费、算力、虚构币种行情三变量持续博弈；离线也赚钱但伴随风险 |
| **反例（红线）** | 可判定的禁止项 | 纯数值堆砌、无成本压力 |
| **可观察的落地** | 玩家能感知到的证据 | 风险事件有"机器在受苦"的强反馈 |

**"反例"是支柱的关键**。只写正面表述时，任何设计都能被解释成"符合支柱"。写不出反例，说明这条支柱还没想清楚。

Hashrise 的三条支柱：

| # | 支柱 | 说明 | 反例（红线） |
|---|------|------|-------------|
| P1 | **真实挂机的经济张力** | 电费、算力、虚构币种行情三变量持续博弈；离线也赚钱但伴随风险 | 纯数值堆砌、无成本压力 |
| P2 | **清晰可读的增长飞轮** | 每次升级都有可感知的算力/收益跃升，反馈即时、进度可见 | 升级感弱、反馈延迟 |
| P3 | **叙事驱动的长线留存** | 用"矿场编年史"把进度变成故事，形成情感锚点 | 剧情与玩法脱钩 |

## 支柱如何映射到具体设计

支柱不能只挂在墙上。要能落到每个子系统：

| 支柱 | 视觉映射 | 机制映射 | 数据映射 |
|------|---------|---------|---------|
| P1 经济张力 | 机器受苦的强反馈（过热发烫、断电变灰） | 风险事件有明确缓解路径 | 电价是永动 sink |
| P2 增长飞轮 | 矿机从 1 台到阵列，ASIC 明显更大更精密 | 每次升级有算力/净收益跃升 | 成本几何曲线 |
| P3 叙事留存 | 老矿主形象 + 章节插画 | 章节由里程碑触发 | 里程碑绑定算力阈值 |

**任何一个新机制，如果三个映射列都填不出内容，它大概率不属于这个游戏。**

## 支柱漂移检查

新机制进来时走这四步：

### 第 1 步 · 声明它服务于哪条支柱

写不出来 → **停**。要么它属于某个尚未定义的支柱（那就先补支柱），要么它是外来物（那就砍掉）。

### 第 2 步 · 检查它是否违反别条支柱的反例

最典型的矛盾组合：

- **P2 增长飞轮 vs P1 经济张力**：新机制让玩家"一键满级"→ 违反 P2 的反例（升级感弱？不，反过来是**成长失去意义**）。这类机制即使"好玩"也会破坏经济。
- **P3 叙事留存 vs P2 增长飞轮**：长篇剧情打断节奏 → 违反 P2 的反例（反馈延迟）。
- **P1 经济张力 vs 玩家友好**：所有操作都要扣钱 → 变成惩罚性设计，违反 P2（升级感弱）。

### 第 3 步 · 给出可观察的落地

"这个机制让游戏更有深度"不是落地。落地是可测的：

- P1 → "玩家在过热前能预见到过热（温度条变红）"
- P2 → "首次升级后，屏幕上每秒产出的数字从 0.35 变成 5.8"
- P3 → "第 2 章在总算力达到 500 H/s 时解锁"

### 第 4 步 · 写进设计文档并更新索引

支柱的落地要落到具体子系统文档，并在系统索引的依赖图里体现。

## 评审用法

评审新机制时，主持人逐条念：

```
这个机制服务于：P__（支柱名）
落地证据：______（可测的一句话）
反例检查：
  - 是否违反 P1 反例？否 / 是（说明）
  - 是否违反 P2 反例？否 / 是（说明）
  - 是否违反 P3 反例？否 / 是（说明）
结论：接受 / 修改后接受 / 拒绝
```

**"修改后接受"是常态**，但"拒绝"必须给出理由——写清楚违反的是哪条反例。

## 目标玩家的对齐

支柱不能脱离目标玩家。Hashrise 的目标玩家画像：

- 放置 / 挂机、模拟经营、轻度策略的**休闲玩家**（移动端碎片化时间）
- 对挖矿、加密题材有好奇或真实经验的群体（真实感壁垒）
- 心理映射以 **Achiever（成就/数值成长）** 为主，**Explorer（解锁新设备/币种）** 为辅

由此推出两个硬约束：

1. **屏内可交互元素 ≤ 6 类**——碎片化时间里的休闲玩家不会读复杂界面。
2. **MVP 必须能完整走通**，不需要长教程。渐进教学在 `hashrise-gdd-author` 的新手引导节里展开。

**支柱与玩家画像冲突时，先怀疑支柱**。支柱是为玩家服务的，不是反过来。

## 常见坑

| 现象 | 根因 | 修法 |
|------|------|------|
| 支柱写了但没人记得 | 支柱没有落地映射 | 每个子系统必须填出机制/数据/视觉三列 |
| 任何设计都能说成"符合支柱" | 没写反例 | 每条支柱必须配可判定的反例 |
| 团队争论"这算不算符合支柱" | 支柱太抽象 | 补充"可观察的落地"一列 |
| 支柱越来越多 | 没有定期合并与淘汰 | 保持在 3–5 条，多了说明在描述功能而非主张 |
| 机制越加越多 | 没做漂移检查 | 新机制必须走四步声明流程 |
| 支柱与目标玩家脱节 | 玩家画像过时 | 定期用真实数据复核画像 |

## 与其他技能的关系

- 支柱是**设计文档总纲**的第一节，写在 `design/gdd/gdd-main.md §1`。
- 每个子系统的"概述"节必须声明它服务于哪条支柱。
- 评审时的一致性红线逐条核对，方法见 `hashrise-gdd-author`。
