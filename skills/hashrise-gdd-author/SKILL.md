# 八节格式 GDD 起草

Hashrise 用一套固定的八节格式写所有子系统设计文档。目的不是好看，而是让**任何一份设计都能被机械地检查**：数值有没有锚定、边界有没有覆盖、验收有没有可执行条目。

## 何时用

- 需要新建或修改 GDD / 子系统设计文档
- 评审别人写的设计文档
- 把口头想法收敛成可交付文档

## 核心约定：数值只认一个源头

所有可调数值必须集中在**总纲的「数值总表」**里，子系统文档只引用不重写。

Hashrise 的做法（`design/gdd/gdd-main.md §3` 为唯一权威源）：

```
gdd-main.md §3 数值总表
   ├─ economy.md      （引用，不重写）
   ├─ upgrade-tree.md （引用，不重写）
   └─ risk-events.md  （引用，不重写）
```

规则：

1. 子系统文档中出现具体数值时，必须标注来源（`见 gdd-main §3.2`）。
2. 要改数值，**先回写总表，再改子系统文档**，顺序不能反。
3. 出现两处不一致时，以总表为准，并在评审记录里记一笔。
4. 代码里的数值同样以总表为准；实现侧应走 Resource 资源化，而不是硬编码（见 `hashrise-godot-architecture`）。

## 八节骨架

每个子系统文档固定这八节，顺序不变：

| # | 节名 | 必须回答 |
|---|------|---------|
| 1 | 概述 Overview | 这个系统解决什么问题？它服务于哪条设计支柱？ |
| 2 | 机制 Mechanics | 具体怎么运转？有哪些变量、状态与触发条件？ |
| 3 | 数据 Data | 数值表、里程碑、节奏。所有数值锚定总表。 |
| 4 | 公式 Formulas | 数学关系。写清变量含义、取值范围与边界。 |
| 5 | 边缘 Edge Cases | 极端情况怎么处理：0、负数、上限、超时、异常。 |
| 6 | UI | 玩家在界面上看到什么？怎么操作？信息层级如何？ |
| 7 | 依赖 Dependencies | 依赖谁、被谁依赖。上游改动会怎样影响我？ |
| 8 | 验收 Acceptance | 可勾选的检查项，每条都能被验证。 |

文档开头写元信息块，标注阶段、依赖与适用范围：

```markdown
> Phase 2 交付物 · 系统设计 (System Design)
> 依赖：economy（产出）、upgrade-tree（跃升）、risk-events（张力）
> 适用范围：本文件为子系统设计总纲；数值以 gdd-main §3 为唯一权威源。
```

## 起草流程

1. **先对齐支柱**。读总纲的设计支柱表（Hashrise 三条：真实挂机的经济张力 / 清晰可读的增长飞轮 / 叙事驱动的长线留存）。写不出"我服务于哪条支柱"的设计，说明还没想清楚。
2. **列依赖图**。先确定上游与下游，再动笔。Hashrise 的依赖是显式画出来的，不是暗示的。
3. **填机制与数据**。数据节里每一张表都要标来源。
4. **写公式时把边界写进去**。离线收益这类公式必须同时给出效率系数与硬上限。
5. **边缘节别偷懒**。"不写边缘 = 没想清楚" 是 Hashrise 的评审铁律。
6. **验收节写成可勾选清单**，每条都能被一个具体动作验证。
7. **自检一致性红线**（见下）。

## 一致性红线（评审必查）

Hashrise 在评审时逐条核对这六条，任何一条不过就退回：

- [ ] 算力 / 电价 / 成本数值与总表 §3 一致
- [ ] **不存在单一"最优解"主导策略**（例如"只买某台机器"就是典型的破坏性最优解）
- [ ] 经济无通胀失控（既有软通涨，也有硬消耗点）
- [ ] 风险事件有明确缓解路径，不做纯随机惩罚
- [ ] 变现只加速、不锁内容（**no pay-to-win 红线**）
- [ ] 认知负载：MVP 屏内可交互元素 ≤ 6 类

## 评审结论写法

不要只写"通过"。Hashrise 的评审结论包含：

```markdown
- **判定：PASS**（附 N 项 CONCERNS，均属计划内延迟决策，不阻塞）
- 一致性红线逐项核对：<逐条结论>
- CONCERNS：
  1. <被推迟的决策及其理由>
  2. <外部依赖，非设计缺陷>
- 退出标准达成，可进入 <下一阶段>。
```

明确区分**设计缺陷**与**计划内延迟决策**，不要用"CONCERNS"糊弄过去。

## 常见坑

- **在子系统文档里自造数值**：最常见。后果是总表与实现各说各话，总表失去权威。
- **边缘节写"暂无特殊情况"**：等于没设计。极端值往往是玩家最先撞到的。
- **验收节写"体验流畅"**：不可验证。改成"连续 30 分钟模拟无异常，帧率不低于 X"。
- **支柱漂移**：新加的机制服务于某条支柱，说不出来源就说明它是这轮新增的，不该混进来。
